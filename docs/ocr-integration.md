# Интеграция с npa-ocr

OCR сканов (бывший «этап 3») выделен 2026-10-12 в отдельный проект
[npa-ocr](https://github.com/EduardIbatullin/npa-ocr) — он не знает о НПА-загрузчике,
принимает просто путь к PDF. История разработки OCR (таблицы, калибровка порогов,
прогоны на реальных документах) — в `docs/plan.md` того репозитория, здесь не
дублируется.

OCR здесь нужен не для всех документов — у `fetch_document()` три уровня, по
убыванию качества и возрастанию цены:

1. **EBPI** (`actual.pravo.gov.ru`, см. [`docs/ebpi-coverage.md`](ebpi-coverage.md))
   — выверенный текст с таблицами. Покрывает законы, указы, постановления/
   распоряжения Правительства, акты высших судов и Банка России — не ведомственные
   приказы.
2. **Механическое извлечение текстового слоя** (`text_layer_docx.py`, без OCR и без
   ИИ) — если EBPI документ не покрыл, но его PDF не скан (текстовый слой есть на
   всех страницах). Срабатывает автоматически внутри `fetch_document()`, результат
   — `result.text_layer_docx_path`. Таблицы и структура не распознаются, только
   текст как он лежит в PDF.
3. **OCR** (этот документ, ниже) — только если PDF — настоящий скан (хотя бы одна
   страница без текстового слоя). Единственный уровень, не вызывающийся
   автоматически из `fetch_document()` — запускается вручную или из веб-UI.

## Граница между проектами

npa-downloader **не импортирует** код npa-ocr. Связь — только через внешний процесс:
`src/npa_pipeline/ocr_jobs.py` (`OcrJobManager`) запускает установленную команду
`npa-ocr` и разбирает её вывод по текстовому контракту:

- **stdout** (один JSON-объект по завершении): `{"docx": "...", "pages": N,
  "pages_ocr_applied": M}` при успехе, либо `{"status": "insufficient_memory",
  "message": "..."}` при нехватке памяти.
- **stderr** (по ходу работы): строки прогресса `[ 23.8%] страница 5 из 21:
  распознаётся` / `готово` / `текстовый слой` / `взято из сохранённого прогона` и
  тайминги шагов `  [стр. 5] таблицы: ...: 1 мин 39 с`.
- **на диске**, рядом с `--out`: `<out>.pages/` (сырые результаты страниц, по ним
  работает возобновление), `<out>.timings.json`.

Полное описание контракта — README npa-ocr, раздел «Внешний контракт». Если он там
поменяется (например, формат JSON или строк прогресса), `ocr_jobs.py` здесь нужно
обновить вручную — автоматической синхронизации между проектами нет.

## Что нужно для работы кнопки «Распознать скан»

Команда `npa-ocr` должна быть на `PATH` того окружения, где запущен веб-сервер
npa-downloader:

```bash
pip install npa-ocr[models]   # в тот же venv/образ, где запущен npa-web
```

Без этого `OcrJobManager.start()` всё равно создаст задание, но процесс сразу
завершится с ненулевым кодом возврата, и задание перейдёт в статус `failed`.

**Открытый вопрос (не решён):** в Docker-образе npa-downloader команда `npa-ocr`
сейчас не установлена (см. комментарий в `Dockerfile`). Кнопка «Распознать скан» в
контейнере работать не будет, пока это не решено — либо ставить `npa-ocr[models]`
в тот же образ (несколько ГБ, системный Tesseract, torch/torchvision CPU — готовый
рецепт есть в `Dockerfile` npa-ocr), либо вызывать его на хосте/в соседнем
контейнере и научить `ocr_jobs.py` обращаться туда (например, HTTP вместо
subprocess) — выбор ещё не сделан.

## Константа DEFAULT_MIN_PAGE_TEXT_CHARS

`ocr_jobs.count_scan_pages()` (для надписи «N страниц без текстового слоя» в
карточке НПА) дублирует порог `DEFAULT_MIN_PAGE_TEXT_CHARS = 20` из npa-ocr —
намеренно, а не импортом (см. docstring модуля `ocr_jobs.py`). Если порог в
npa-ocr изменится, здесь его тоже нужно поправить вручную, иначе счётчик страниц
в UI разойдётся с тем, что реально распознает `npa-ocr`.
