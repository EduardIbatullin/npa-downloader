# Интеграция с npa-ocr

OCR сканов (бывший «этап 3») выделен 2026-10-12 в отдельный проект
[npa-ocr](https://github.com/EduardIbatullin/npa-ocr) — он не знает о НПА-загрузчике,
принимает просто путь к PDF. История разработки OCR (таблицы, калибровка порогов,
прогоны на реальных документах) — в `docs/plan.md` того репозитория, здесь не
дублируется.

OCR здесь нужен не для всех документов — у `fetch_document()` три уровня, по
убыванию качества и возрастанию цены:

1. **EBPI** (`actual.pravo.gov.ru`, см. [`docs/ebpi-coverage.md`](ebpi-coverage.md))
   — выверенный текст с таблицами. Покрывает законы, указы, постановления/
   распоряжения Правительства, акты высших судов и Банка России — не ведомственные
   приказы.
2. **Механическое извлечение текстового слоя** (`text_layer_docx.py`, без OCR и без
   ИИ) — если EBPI документ не покрыл, но его PDF не скан (текстовый слой есть на
   всех страницах). Срабатывает автоматически внутри `fetch_document()`, результат
   — `result.text_layer_docx_path`. Таблицы и структура не распознаются, только
   текст как он лежит в PDF.
3. **OCR** (этот документ, ниже) — только если PDF — настоящий скан (хотя бы одна
   страница без текстового слоя). Единственный уровень, не вызывающийся
   автоматически из `fetch_document()` — запускается вручную или из веб-UI.

## Граница между проектами

npa-downloader **не импортирует** код npa-ocr и не устанавливает его в свой образ.
Решено (2026-10-14): связь — отдельный сервис, HTTP, не общий образ и не Docker-
сокет (варианты и их компромиссы разбирались при решении — здесь не дублируется).
`npa-ocr` отдаёт свой образ, умеющий работать в двух режимах (CLI — по умолчанию,
и HTTP-сервер — другой входной командой, см. его README, «HTTP API»); в
`docker-compose.yml` здесь — второй сервис, `ocr`, со своим контейнером, в общей
сети compose (имя сервиса = DNS-имя, `http://ocr:8000`, без общего тома и без
проброса порта наружу).

`src/npa_pipeline/ocr_jobs.py` (`OcrJobManager`) — тонкий HTTP-клиент к этому
сервису: отправляет PDF (`POST /jobs`, multipart), опрашивает прогресс
(`GET /jobs/{id}`), скачивает готовый `.docx` (`GET /jobs/{id}/result`), когда
статус стал `"done"`. Адрес сервиса — переменная окружения `OCR_SERVICE_URL`
(в compose — `http://ocr:8000`; без compose, при локальной разработке —
`http://localhost:8000` по умолчанию). Сервис сам управляет тяжёлыми моделями и
ограничением «одно задание одновременно» (вернёт `409`, если занят) — здесь это
только транслируется в `JobBusyError`. Сбой сети до сервиса — `OcrServiceUnavailableError`
(веб-API отдаёт `503`), не падение всего процесса.

Контракт ответов сервиса (`status`/`percent`/`page`/`total_pages`/`page_status`/
`steps`/`elapsed_seconds`/`return_code`/`error`) — README npa-ocr, «HTTP API». Если
он там поменяется, `ocr_jobs.py` здесь нужно обновить вручную — автоматической
синхронизации между проектами нет.

## Что нужно для работы кнопки «Распознать скан»

Сервис `ocr` должен быть поднят и доступен по `OCR_SERVICE_URL` — для
`docker-compose.yml` это значит, что образ `npa-ocr:latest` должен существовать
локально (собирается отдельно, в репозитории npa-ocr: `docker build -t npa-ocr .`)
до `docker compose up`. Без этого `OcrJobManager.start()` бросает
`OcrServiceUnavailableError`, веб-API отвечает `503` — задание не создаётся
вообще (раньше, при subprocess-схеме, задание создавалось и сразу падало в
`failed`; сейчас ошибка видна раньше и яснее).

Модели (PaddleOCR, TATR, torch) требовательны к памяти — сервис разрешает не
больше одного задания одновременно (см. его README) независимо от того, сколько
клиентов его дёргают. Образ `npa-ocr` уже содержит все модели, закачанные на
этапе сборки (не при первом запросе) — см. его README и `Dockerfile`,
`scripts/preload_models.py`.

## Константа DEFAULT_MIN_PAGE_TEXT_CHARS

`ocr_jobs.count_scan_pages()` (для надписи «N страниц без текстового слоя» в
карточке НПА) дублирует порог `DEFAULT_MIN_PAGE_TEXT_CHARS = 20` из npa-ocr —
намеренно, а не импортом (см. docstring модуля `ocr_jobs.py`). Если порог в
npa-ocr изменится, здесь его тоже нужно поправить вручную, иначе счётчик страниц
в UI разойдётся с тем, что реально распознает `npa-ocr`.
