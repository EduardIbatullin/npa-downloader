# Справочник по поисковому API ips.pravo.gov.ru

Факты в этом документе получены эмпирическим тестированием (разбор минифицированного
React-бандла сайта + прямые запросы к живому API) — официальной документации у этого
API нет. Дата проверки: 2026-10-13.

Отдельный документ от [`docs/status-sources-reference.md`](status-sources-reference.md):
там описан только `document_card.json` (требует уже известный `eoNumber`), здесь —
`search.json` и соседние методы, которые находят документ **без** `eoNumber`.

## Зачем

`publication.pravo.gov.ru` (на нём построен весь поиск этапа 1, `search.py`) не
покрывает документы старше ~08.11.2011 (см. `models.COVERAGE_START`) — у них просто
нет `eoNumber`. До этой находки у проекта не было способа найти такой документ по
реквизитам вообще, только читать его, если `eoNumber`/внутренний id уже известен
из внешнего источника (КонсультантПлюс, Гарант, Wikisource и т.п.).

## Статус интеграции — резерв только для документов старше границы охвата

Решение (2026-10-13): подключать этот API только как fallback внутри
`search_document()`, когда основной поиск на `publication.pravo.gov.ru` закончился
`out_of_range` — не как замену или параллельный путь для документов в пределах
обычного охвата.

Причина: `/api/Documents` на `publication.pravo.gov.ru` — проверенный, со
структурированными полями (номер/дата/орган/тип отдельно), уже встроен во весь
алгоритм (`match_type`, `ambiguous`, диагностика). `search.json` — недокументированный
React-эндпоинт, с менее структурированным ответом (реквизиты одной строкой в
`adoption`, нужен парсинг) и без каких-либо гарантий стабильности. Подключать его
для документов, которые и так находятся основным путём, увеличивало бы хрупкость
без выигрыша. Для документов старше границы охвата альтернативы у проекта вообще
не было — там выигрыш однозначен.

## Как устроен сайт

`http://ips.pravo.gov.ru/` — React-приложение (ИПС «Законодательство России»):
статический HTML пустой (`<div id="root">`), весь интерфейс и вызовы API — в
`main.js` (~2.4 МБ минифицированного кода). API искался тем же способом, что и для
EBPI (`docs/ebpi-coverage.md`) — grep по строкам `"/api/..."` в бандле, затем прямые
запросы для проверки гипотез.

## Найденные эндпоинты

Все проверенные запросы не требуют авторизации, `robots.txt` на хосте отсутствует
(404) — ограничений не заявлено.

### `GET /api/ips/legislation/bpas.json`

Список доступных баз. На момент проверки — одна:

```json
[{
  "name": "Федеральное законодательство",
  "bpas": [{
    "name": "ФЕДЕРАЛЬНОЕ ЗАКОНОДАТЕЛЬСТВО",
    "id": 102000001,
    "first": "28.07.1952",
    "last": "06.10.2026",
    "size": 252123,
    "baseid": "c000000000"
  }],
  "id": 1
}]
```

`baseid: "c000000000"` — значение параметра `bpas` для `search.json` и
`bpa-*.json` ниже. Диапазон охвата — **с 28.07.1952**, то есть вся советская и
российская федеральная история, не только период после 2011 года.

### `POST /api/ips/legislation/search.json` — главная находка

`Content-Type: application/x-www-form-urlencoded`. Тело — набор полей поиска,
без JSON-обёртки:

```
searchType=attrSearch&number_eq=7-ФЗ&date=10.01.2002,10.01.2002&bpas=c000000000&page=1
```

Проверено на реальном документе (Федеральный закон от 10.01.2002 № 7-ФЗ «Об охране
окружающей среды» — заведомо старше границы охвата `publication.pravo.gov.ru`):

```json
{
  "wording": { "number_eq": "7-ФЗ", "date": "10.01.2002,10.01.2002", "sort": [...] },
  "docs": [{
    "state": "Действует с изменениями",
    "name": "Об охране окружающей среды",
    "adoption": "Федеральный закон от 10.01.2002 № 7-ФЗ",
    "docdate": "10.01.2002",
    "nd": "1000000000102074303",
    "hash": "2dfaf5368f2d181af77269d1009c4532bc62e8c01d443478747808afc3b4fa35",
    "image": null,
    "baseid": "c000000000",
    "publications": ["\"Российская газета\" от 12.01.2002 г.", "..."],
    "rank": 9999
  }],
  "pageSize": 1,
  "page": 1
}
```

Поля ответа:
- `nd` — внутренний идентификатор документа в этой системе (не `eoNumber`; для
  документов, у которых `eoNumber` есть, `image` содержит прямую ссылку на
  `publication.pravo.gov.ru/document/<eoNumber>` — `null`, если документа там нет,
  как в примере выше).
- `state` — статус текстом (`"Действует без изменений"` / `"Действует с
  изменениями"` / вероятно `"Утратил силу"` — не проверено на реальном примере).
- `adoption` — реквизиты одной строкой (орган, дата, номер) — не разбито на поля,
  в отличие от `/api/Documents` на `publication.pravo.gov.ru`; разбор потребует
  парсера, аналогичного `parse_citation.py`.
- `hash` — хеш документа в системе (назначение не исследовано дальше).

**Поля запроса, разобранные из `main.js` (карта URL-ключ → внутреннее имя):**

| URL-параметр | Значение |
|---|---|
| `number` | номер, нечёткое совпадение (тип 1 — подстрока/похожесть) |
| `number_eq` | номер, точное совпадение (тип 2) — использован в примере выше |
| `date` | диапазон `"DD.MM.YYYY,DD.MM.YYYY"` (проверено: формат с точками, не ISO — `2002-01-10,2002-01-10` не сработал, `10.01.2002,10.01.2002` сработал) |
| `organ` | орган-подписант, строковое имя (не GUID/код) из `bpa-organ.json` |
| `bpas` | `baseid` базы — `c000000000` для единственной известной базы |
| `searchType` | `attrSearch` (поиск по реквизитам — как здесь), `smartSearch`/`hybridSearch` — текстовый/гибридный, не проверялись |
| `page` | номер страницы результатов |

**Не доведено до конца: фильтр `organ`.** Запрос с `organ=Президент` на тот же
документ вернул пустой результат (без ключа `docs`) — значение не совпало с тем,
что реально хранится у документа. Список `bpa-organ.json` (47 органов) при первом
просмотре (первые 20) не содержит ни «Президент», ни «Президент Российской
Федерации» как отдельного значения — есть только составные («Государственно-
правовое управление Президента» и т.п.). Не выяснено: правильное значение для
федеральных законов — другое имя, нужна вторая страница списка органов, или
`organ` в принципе не фильтрует федеральные законы так, как ожидалось. **Запрос
без `organ` (только `number_eq` + `date`) уже дал однозначное попадание** — для
большинства случаев фильтр по органу может быть не обязателен, если номер+дата
уникальны в пределах базы.

### Полная цепочка «найти → карточка → текст» — подтверждена на реальном документе

После `search.json` (выше) оставшиеся два шага дают полный текст действующей
редакции, без EBPI и без `eoNumber`:

**`GET /api/ips/legislation/document_card.json?nd=<nd>&bpa=<baseid>`** — та же
карточка, что описана в `docs/status-sources-reference.md` для `pubnumber=`, но по
внутреннему `nd` вместо `eoNumber` (параметры взаимозаменяемы — какой передать,
зависит от того, что уже известно). На ФЗ-7/2002 отдала полную карточку: `state`,
`keywords`, `officers` (`"В.Путин"`), `hash`, и ключевое — **`redactions[]` с 102
записями**. Каждая запись:

```json
{
  "id": 99,
  "actual": true,
  "date": "01.09.2026",
  "status": "актуальная",
  "onumber": "304-ФЗ", "odate": "31.07.2025",
  "refadoption": "Федеральный закон от 31.07.2025 № 304-ФЗ",
  "refnd": "1000000000607599126",
  "refhash": "e66e99a0ed...",
  "comment": "ст. 1, 5, 23, ...",
  "size": 916177
}
```

**Исправление (2026-10-14):** в предыдущей проверке значения `status` были
прочитаны неверно — кириллица в выводе `curl` в терминале отображалась
побайтово искажённой (mojibake между UTF-8 и cp1251), и реконструкция вручную
дала неправильные слова («применяется», «не вступила в силу»). Повторная
проверка скриптом, пишущим ответ в файл как UTF-8 (без расшифровки на глаз),
дала настоящие значения: у документа 102 редакции со `status` из трёх вариантов
— `"недействующая"` (99 из 102, уже не действуют), `"актуальная"` (ровно одна —
текущая редакция, здесь `id: 99`), `"не вступившая в силу"` (2, будущие). Код
(`npa_pipeline.ips_pravo.select_latest_redaction`) выбирает по этим трём, а не
по `"применяется"`/`"не вступила в силу"` — **урок**: не доверять кириллице,
прочитанной глазами из вывода терминала, если есть способ сравнить программно.

`id` — это `rdk` (redaction key) для следующего шага. `actual: true` + `status:
"актуальная"` — текущая действующая редакция (в отличие от EBPI, здесь поле
`actual` совпало со status на единственном проверенном документе — не
гарантия на других, см. «Открытые вопросы»). `refnd` — `nd` акта-поправки, тот
же принцип, что `reddocrefid`→`docid` у EBPI (`resolve_amending_acts`): можно
резолвить, чем внесена эта редакция, тем же `document_card.json?nd=<refnd>`.
Будущие редакции тоже есть в списке со `status: "не вступившая в силу"` — у
ФЗ-7/2002 такие были на момент проверки (эффективны с 01.01.2027 и 01.03.2028).

**`GET /api/ips/legislation/documenttext?nd=<nd>&bpa=<baseid>&rdk=<id>&completed=true`**
— сам текст. **`completed=true` обязателен** — без него эндпоинт отдаёт `200 OK` с
пустой строкой `doctext: ""` (похоже на пустой ответ по ошибке, а не на отказ —
легко принять за «текста нет», это не так). С `completed=true` отдаёт:

```json
{"docid": "...", "doctext": "<!DOCTYPE html>...", "rdk": 99, "baseid": "c000000000"}
```

На ФЗ-7/2002 — **588 КБ HTML**, тот же стиль Word-экспорта, что у EBPI
(`xmlns:w="urn:schemas-microsoft-com:office:word"`), и те же имена CSS-классов
абзацев (`p.Y` встретился в хвосте документа — см. разметку в
`docs/ebpi-coverage.md`, «Формат текста»). Внутри текста ссылки на поправки — через
`documenttext?hash=<refhash от redactions[]>` (без `nd`/`rdk`/`completed` — другая,
более короткая форма того же эндпоинта, не проверена отдельно).

**Подтверждено реальным прогоном (2026-10-14):** `ebpi_docx.py::convert_redtext_to_docx()`
применяется к этому HTML без изменений — отдельный конвертер не понадобился.
На ФЗ-7/2002: 1794 абзаца (1513 непустых), 0 таблиц (у этого документа их нет),
включая шапку («РОССИЙСКАЯ ФЕДЕРАЦИЯ», «ФЕДЕРАЛЬНЫЙ ЗАКОН», полный список
изменяющих актов) и подпись («Президент Российской Федерации В.Путин», место и
дата). Таблицы отдельно не проверены (нужен документ с таблицей среди текстов
`ips.pravo.gov.ru`, чтобы подтвердить и эту часть разметки, а не только абзацы).

### Другие найденные, но не проверенные эндпоинты

Из того же грепа по `main.js` — вероятно существуют и работают, не протестированы:

- `GET /api/ips/legislation/document_refs.json` — вероятно, связи («кем изменён»,
  «что изменяет»), отдельно от `redactions[]` выше.
- `GET /api/ips/legislation/search_prompt.json` / `common-search.json` — автодополнение
  и текстовый поиск, отдельные от `attrSearch`.
- `GET /api/ips/legislation/bpa-doctype.json`, `bpa-region.json`, `bpa-keyword.json`,
  `bpa-edition.json` — справочники для остальных фильтров поиска (вид акта, регион,
  ключевые слова, издание) — не проверялись.
- `GET /api/ips/legislation/document_file`, `document_supplements.json` — вероятно,
  приложения/файлы к документу — не проверялись.

## Независимая проверка чтения (другим путём)

Страница `http://pravo.gov.ru/proxy/ips/?nd=102074303` (старый, не-React
просмотрщик того же хоста, обнаруженный независимо через внешнюю цитату на
Wikisource) показывает текст того же закона с правками **до 04.08.2026 № 330-ФЗ**
включительно — подтверждает, что `ips.pravo.gov.ru` ведёт действующую редакцию
активно, не только хранит исходную публикацию. `nd=102074303` в URL этого
просмотрщика — не то же число, что `nd` в ответе `search.json`
(`1000000000102074303`); похоже, это две разные, но связанные формы одного
идентификатора (возможно, старый просмотрщик обрезает/перекодирует общий префикс) —
точное соответствие не выяснено, не было нужно для доказательства факта.

## Контракт результата — новый статус `FOUND_TEXT_ONLY`

Решение (2026-10-14): результат, когда резерв нашёл ровно одного кандидата и отдал
текст, — **новый элемент `Status.FOUND_TEXT_ONLY`**, не `Status.FOUND` с
`pdf_path=None`.

Причина: во всей системе `Status.FOUND` неявно подразумевает, что `pdf_path`
заполнен — документ сначала скачивается как PDF с `publication.pravo.gov.ru`,
`ebpi_docx_path`/`text_layer_docx_path` лишь дополняют уже существующий файл.
У документов из этого резерва PDF структурно не существует — есть только
HTML-текст (`documenttext`). Явный новый статус заставляет код, который разбирает
`Status` (CLI, `webapp.py`, веб-UI), осознанно добавить обработку этого случая,
а не тихо получить `pdf_path is None` там, где раньше это не предполагалось —
на момент решения `pdf_path` использовали 7 файлов в `src/npa_pipeline/`, ни один
не проверялся на этот случай.

Для нуля совпадений в `search.json` — остаётся `Status.OUT_OF_RANGE` (см. ниже,
меняется только смысл и сообщение). Для нескольких совпадений — `Status.AMBIGUOUS`
с отдельным полем `ips_candidates` (решение см. ниже, «Несколько совпадений»).

Поля результата (`Result`, по аналогии с `ebpi_docx_path`/`ebpi_docstate`):
- `ips_nd` — внутренний идентификатор документа в ips.pravo.gov.ru (`nd`).
- `ips_docx_path` — .docx из `documenttext` (конвертер — переиспользуемый
  `convert_redtext_to_docx`, без изменений, см. выше — подтверждено реальным
  прогоном).
- `ips_state` — статус редакции текстом (`redactions[].state`).
- `ips_adoption` — реквизиты одной строкой, как отданы API (`adoption`).
- `ips_candidates: list[dict[str, Any]]` — заполняется только при `AMBIGUOUS` из
  этого резерва (см. ниже), по одному словарю `{"nd", "adoption", "docdate",
  "state", "publications"}` на кандидата.

### Несколько совпадений (`AMBIGUOUS`)

Решено (2026-10-14): не переиспользовать `Result.candidates: list[DocItem]` —
`DocItem` рассчитан на структурированные поля `publication.pravo.gov.ru`
(`eo_number` обязателен), которых у находок `ips.pravo.gov.ru` нет. Вместо этого —
отдельное поле `ips_candidates: list[dict[str, Any]]`, тот же приём, что уже
применён для `ItsResult.candidates: list[dict[str, Any]]` (там кандидаты тоже из
структурно другого источника, поэтому не `DocItem`). `candidates` при этом
остаётся пустым — потребителям (`CLI`, `webapp.py`, UI), разбирающим `AMBIGUOUS`,
нужно проверять оба поля.

`pdf_path` в этом случае всегда `None` — не ошибка, структурная особенность
источника (так же, как у `ItsFileResult.pdf_path` уже штатно бывает `None`, когда
файл не PDF).

## Отдача .docx через веб-UI

Реализовано (2026-10-14): `ips_docx_path` хранится только в Result конкретного
запроса — без отдельной таблицы в БД `GET /api/docx/{nd}` (webapp.py) не мог бы
отдать файл по отдельному HTTP-запросу (открытие в новой вкладке, повторный
визит на страницу). Таблица `ips_documents` (nd PRIMARY KEY, adoption, state,
docx_path, found_at; без FK на `documents` — структурно другой источник) пишется
в `service._try_ips_fallback` при каждом успешном нахождении текста. Побочный
эффект, не только для веб-отдачи: повторный поиск того же документа (тот же nd)
переиспользует уже готовый .docx, не плодит `..._2.docx` и не перезапрашивает
карточку/текст у ips.pravo.gov.ru заново.

`GET /api/docx/{nd}` — тот же паттерн, что `/api/pdf/{eo_number}` и
`/api/its/pdf/{file_id}`; `?download=1` — `Content-Disposition: attachment`,
без него — `inline`. В выдаче `_lookup_npa()`/`api_fetch()` при заполненном
`ips_docx_path` в `files` добавляется кнопка «DOCX (ips.pravo.gov.ru)» — рендерит
её уже существующий общий `fileActions()` в `app.js`, фронтенд не менялся.

Проверено вручную: реальный поиск ФЗ-7/2002 через `/api/lookup` поднятого
`npa-web` → `found_text_only` с кнопкой DOCX → `GET /api/docx/<nd>` отдал тот же
142 КБ файл, что и в более ранней прямой проверке конвертера (см. выше).

## `OUT_OF_RANGE` меняет смысл

Решение (2026-10-14): после этой интеграции `Status.OUT_OF_RANGE` означает не
просто «дата раньше границы охвата», а «дата раньше границы охвата, **и** резерв
через `ips.pravo.gov.ru` не дал ровно одного совпадения» (ноль — см. выше). Текущее
сообщение («раньше границы охвата») вводит в заблуждение после этой интеграции —
нужно переформулировать так, чтобы было ясно, что попытка через резерв была и не
дала однозначного результата, а не что её не делали вовсе.

## Открытые вопросы

- Фильтр `organ` — см. выше, не выяснен до конца.
- Статус документа целиком, когда он отменён (аналог `minustdate`/`minustnum` у
  `document_card.json` на `publication.pravo.gov.ru`, которые там оказались
  бесполезны) — не проверено на реально отменённом документе; какое значение
  принимает верхнеуровневое `state`/`status` в этом случае, не известно.
- Поле `actual` в `redactions[]` — на единственном проверенном документе совпало
  со `status == "актуальная"`. У EBPI аналогичное поле оказалось ловушкой (см.
  `docs/ebpi-coverage.md`) — не считать это поле надёжным для выбора редакции
  без системной проверки на нескольких документах, выбирать по `status`, как и
  сделано в `ips_pravo.select_latest_redaction`.
- Таблицы в `documenttext` — конвертер (`convert_redtext_to_docx`) подтверждён
  только на документе без таблиц (ФЗ-7/2002). Разметка таблиц калибровалась по
  документам EBPI — не проверено, что она совпадает и здесь.
- `document_content` (структура/оглавление документа — проверено, работает) всё
  ещё не до конца понятен для случая, когда нужен не весь текст, а конкретный
  параграф/статья — не исследовалось, т.к. `documenttext` с `completed=true` уже
  даёт полный текст целиком.
- Полное покрытие `number`/`number_eq` на двусмысленных случаях (несколько
  документов с одним номером в разные годы — как `№7-ФЗ`, встречается почти
  каждый год) не проверено с фильтром `date`, сужающим до точного дня: один тест
  это подтвердил, системной проверки на выборке нет.
- Авторизационные эндпоинты (`/api/personal/*`, `/api/admin/*`) в бандле есть, но
  не нужны и не исследовались — поиск и чтение работают полностью анонимно.
