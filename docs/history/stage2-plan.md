# Этап 2 — статус документа и история изменений

Предварительный черновик плана, прошёл раунд предметного разбора (включая проверку по фактическому коду БД и по `robots.txt` источников). Не финальная версия. Детали по источникам — [`docs/status-sources-reference.md`](status-sources-reference.md).

## Цель

Для документа, уже найденного и скачанного на этапе 1 (есть `eoNumber`, орган, номер, дата, тип), определить:
1. **Статус** — действует / действует с изменениями / не действует (утратил силу) / иной (см. контракт — реальных статусов больше трёх).
2. **Если не действует** — каким актом, датой самого акта и датой вступления отмены в силу (это разные даты, см. ниже).
3. **Список изменяющих документов** — номер, дата, что изменено, и по возможности их собственный `eoNumber`.

Без ИИ в рантайме, как и этап 1.

## Блокирующий вопрос перед реализацией: `robots.txt`, и он касается не только этапа 2

Проверил `docs.cntd.ru/robots.txt` — там явно:
```
Disallow: /*?
Disallow: /search?
Disallow: /api
```
Прямой запрет на программные запросы с query-параметрами, включая ровно тот эндпоинт (`/search?q=...`), на котором построен резолвинг документа по реквизитам в этом плане. Карточки документов (`/document/<ID>`) не запрещены.

**Тот же вопрос обнаружился и у `publication.pravo.gov.ru` (источник этапа 1)**: `Disallow: /Search`, `Disallow: /File` — а этап 1 скачивает PDF через `/file/pdf?eoNumber=...`. Путь в `robots.txt` регистрочувствителен (`/File` ≠ `/file` по букве стандарта), но сервер на IIS не различает регистр в маршрутизации — то есть по факту это тот же ресурс, и намерение владельца («не разрешаем ботам скачивать файлы») очевидно, даже если буквальное совпадение строк спорное. `/api` при этом чистый — сам поиск по API не запрещён ни у одного из двух источников этапа 1/2, запрещены собственно человеко-ориентированные `/Search`/`/File`/`/search?`, не JSON API.

`ips.pravo.gov.ru` — `robots.txt` отсутствует (404), ограничений не заявлено.

**Это не два разных вопроса для двух этапов — это один вопрос для всего проекта**, и его нужно решить один раз, единым принципом, а не по-разному для каждого источника:

> `robots.txt` адресован краулерам — программам, которые массово обходят сайт. Разовое получение конкретного документа по запросу человека — вероятно, приемлемая серая зона. Массовый/фоновый сбор (отложенный режим 3 этапа 1, регулярная фоновая перепроверка статуса на этапе 2) — это уже ровно то поведение, которое `robots.txt` описывает и запрещает.

Даже там, где путь технически не запрещён `robots.txt` (карточки `/document/<ID>`, `/api/Documents`) — пользовательское соглашение владельца сайта может отдельно запрещать автоматическое копирование; искал отдельный текст соглашения «Кодекса» — не нашёл, только общую копирайт-строку в подвале сайта. Это не снимает вопрос, а показывает, что ответ можно получить только напрямую у владельца.

**Практический шаг, закрывающий вопрос для обоих этапов одним действием**: написать в АО «Кодекс» с вопросом про партнёрский/API-доступ (по аналогии с тем, как выяснился платный API у Гаранта) — ответ либо даст легальный путь, либо явно закроет вопрос. Заодно уточнить границу «разовый запрос / массовый сбор» — не считать её решённой одним предположением из этого плана.

До ответа от «Кодекса»: раздел «Резолвинг через `docs.cntd.ru`» ниже — **условный дизайн, не план к реализации**. Этап 1 (уже реализованный) использует `/file/pdf` — та же оговорка касается и его, отдельным пунктом в `stage1-plan.md`.

## Общая схема (при условии, что вопрос про `docs.cntd.ru` решён в пользу использования)

1. **`ips.pravo.gov.ru`** — пробуем первым, но только если орган-подписант входит в список 5 покрытых (Президент, Правительство, Госдума, Совет Федерации, Конституционный Суд — GUID уже есть в справочнике органов этапа 1). Если орган не из этого списка — сразу пропускаем этот шаг, не тратим запрос на заведомый 404.
2. **`docs.cntd.ru`** — если орган не из покрытых. Резолвинг по реквизитам (см. блокирующий вопрос выше), при успехе даёт полные и точные данные, **включая регионы** (проверено — см. ниже).
3. **Резервные источники** (`base.garant.ru`, `bazanpa.ru`, `rulaws.ru`) — **в первой версии не используются как источник статуса**. Оба свободных агрегатора (`bazanpa.ru`, `rulaws.ru`) на проверке пропустили реальную правку — статус с них ненадёжен, а маркировка `unverified` в выдаче слишком легко читается пользователем как «действует». Если резолвинг через `docs.cntd.ru` не дал результата — возвращаем `unknown` и прикладываем найденных кандидатов (ссылки) как подсказку человеку, не как ответ.

   Рассматривался вариант «искать ID через `bazanpa.ru`/`rulaws.ru` (их поиск не запрещён их правилами), а карточку статуса читать на `docs.cntd.ru`» — **проверено, не работает**: страницы `bazanpa.ru`/`rulaws.ru` не содержат ссылок на `docs.cntd.ru`, сайты никак не связаны. `Sitemap` из `robots.txt` `docs.cntd.ru` тоже проверен (как у Гаранта — только `<loc>`+`<lastmod>`, без названий/номеров) — не годится для сопоставления по реквизитам. Легального обхода блокирующего вопроса выше не нашлось — решается только напрямую с «Кодексом».
4. Ничего не нашлось — `unknown`, явно.

## Алгоритм

1. Если орган-подписант не входит в список 5 покрытых `ips.pravo.gov.ru` — пропустить шаг 2, перейти к шагу 3.
2. `GET ips.pravo.gov.ru/.../document_card.json?pubnumber=<eoNumber>`. Если 200 — источник **authoritative**: `state` — статус; если `"Утратил силу"` — редакция с `actual: true` даёт `onumber`/`odate`/`refadoption` отменяющего акта; весь `redactions[]` (кроме нулевой записи) — список правок. **Открытая подзадача**: у записей `redactions[]` есть только `onumber`/`odate`/`refadoption` (текстовая цитата), не `eoNumber` — чтобы получить `eoNumber` каждой правки (нужно для цели 3 плана и для прямой скачки через этап 1), придётся разобрать `refadoption` на орган+тип+номер+дату и прогнать через алгоритм этапа 1 отдельным вызовом. В план это включено как отдельный подшаг, не решается «само собой». Готово, конец.
3. Резолвинг через `docs.cntd.ru` (при условии решения блокирующего вопроса выше):
   - Запрос из реквизитов (тип+орган+номер+дата, нормализация номера как в этапе 1).
   - Распарсить ссылки `/document/<ID>` из результата.
   - Если несколько кандидатов — сверка **сначала по `eoNumber`** (в структурированном блоке `publications`/`registrations` на странице кандидата, если поле присутствует), и только если `eoNumber` не найден в данных cntd — по номеру+дате+органу с той же дисциплиной «не угадывать» (0 или >1 совпадений — явные статусы, не выбор первого). **Важно**: `eoNumber` присутствует не на всех документах — проверено, что на объёмных/старых документах (пример: закон, изменяемый 200+ раз) поле `publications` может не содержать `eoNumber` вовсе, тогда сопоставление только по номеру+дате+органу.
   - Если найден ровно один кандидат — разобрать статус-метку, блок отмены («Утратил силу с `<дата вступления в силу отмены>` на основании `<орган>` от `<дата акта>` № `<номер>`» — две даты, обе сохраняются отдельно), и блок «Информация об изменяющих документах» (регуляркой — номер+дата+`eoNumber`, когда он указан).
   - Источник — **verified** (проверено на 3 реальных случаях: действующий с правками, отменённый, региональный — все совпали с независимо подтверждённой правдой), но это эмпирика на малой выборке, не официальная гарантия.
4. Если резолвинг не дал однозначного результата — `unknown` + ссылки на найденных (неоднозначных) кандидатов как подсказка.

## Региональные акты — покрытие `docs.cntd.ru` подтверждено

Проверено на реальном примере: Постановление Правительства Санкт-Петербурга №719 от 08.09.2026 — найдено, статус «Действующий», `eoNumber` совпал точно. Это важно, поскольку в кэше органов этапа 1 регионов — 3846 из 3986, то есть подавляющее большинство подписантов, для которых `ips.pravo.gov.ru` не работает, относятся именно к этой категории.

## Массовая сверка `docs.cntd.ru` против `ips.pravo.gov.ru` — сделана на 1 документе, не более

Точная сверка «статус на cntd совпадает со статусом на ips для одного и того же документа, покрытого обоими» пока сделана только на **одном** документе (ФЗ №229-ФЗ, отменённый — статус и реквизиты отмены совпали). Остальные проверки cntd (Минприроды №434, №214, СПб №719) сравнивались с ранее независимо подтверждённой правдой из Гаранта, не напрямую с `ips.pravo.gov.ru`. **n=1**, не «малая выборка» в смысле статистической значимости — этого недостаточно для уверенной метки `verified`, нужна полноценная сверка на 50–100 документах, покрытых обоими источниками, перед тем как закладывать `docs.cntd.ru` как основной резерв в реализации.

## `rulaws.ru`: непроверенная возможность для обратной задачи

Чекбокс **«Документы "о внесении изменений"»** (`is_making_change`) в форме поиска `rulaws.ru` — потенциальный самостоятельный способ решить обратную задачу («какие документы изменили X»), независимый от `docs.cntd.ru`. Не тестировался. Полезен для перекрёстной проверки полноты списка правок, если окажется рабочим.

## Контракт результата

- `status`: `in_force` | `in_force_amended` | `repealed` | `not_yet_in_force` | `other` | `null`. **`null`** — единственный корректный статус, когда `confidence: unknown` (ничего не найдено нигде, см. ниже) — до этой правки в контракте не было значения для этого случая, хотя `confidence: unknown` его явно описывает; статус из пяти содержательных вариантов присваивается, только если что-то реально найдено. При `other` (и в целом всегда, когда есть результат) сохраняется `raw_status_text` — исходная формулировка источника, чтобы не втискивать реальные случаи («приостановлен», «утратил силу частично» и т.п.) в один из заготовленных вариантов. **`not_yet_in_force` пока не подтверждён эмпирически** ни на `ips.pravo.gov.ru` (наблюдались только `"Действует без изменений"` / `"Действует с изменениями"` / `"Утратил силу"`), ни на `docs.cntd.ru` (наблюдались только `"Действующий"` / `"Недействующий"`) — включён в контракт по аналогии с найденным у Гарант Коннект перечнем статусов (`действующие/утратившие силу/не вступившие в силу`), источником, который в этом плане фактически не используется. Не удалять как заведомо ошибочный, но и не считать проверенным — если после реализации ни один из двух источников никогда не вернёт такой статус, стоит убрать значение из контракта, а не оставлять недостижимым.
- `repealed_by` (если `repealed`): `{number, date, effective_date, eo_number?}` — `date` (дата самого отменяющего акта) и `effective_date` (дата, с которой отмена реально действует) — разные поля, не путать (пример: приказ №214 — акт от 13.08.2025, `effective_date` 18.10.2025).
- `amendments[]`: список `{number, date, eo_number?, note?}` — поле `note` соответствует `comment` из ответа `ips.pravo.gov.ru` (какая статья/пункт изменены).
- `source`: `ips.pravo.gov.ru` | `docs.cntd.ru` | `none`.
- `confidence`: `authoritative` (ips.pravo.gov.ru) | `verified` (docs.cntd.ru) | `unknown` (ничего не нашлось; при неоднозначном резолвинге — прикладываются кандидаты-подсказки, но `confidence` всё равно `unknown`).
- `checked_at`: дата проверки.

## Хранение — новая таблица, `document_relations` не расширяется под статус

Прочитал `src/npa_pipeline/db.py`: `document_relations.target_eo` уже `NULL`-совместим и рядом уже есть `target_ref_text` — то есть связь с ещё не скачанным изменяющим документом туда пишется уже сейчас, без изменений схемы. Но:
- статусу самого документа (действует/не действует) в текущей схеме действительно негде храниться — это свойство документа на момент проверки, не связь между двумя документами;
- полей `source`/`confidence`/`checked_at` в `document_relations` нет.

Решение: отдельная таблица **`document_status_checks`** — `(id, eo_number, status, raw_status_text, source, confidence, checked_at, raw_payload)`. Каждая проверка — отдельная строка (видна история, не только последнее состояние).

**Направление связи в `document_relations` — фиксируется явно, сейчас, до первой вставки.** Проверил `db.py` — сейчас там нет ни одного комментария о направлении и ни одной функции вставки (таблица не используется кодом), то есть решение можно принять один раз и сразу закрепить, не переделывая позже. Конвенция:
- `source_eo` = документ, который проверяется (тот, что изменили/отменили) — всегда уже известен, есть в `documents`, отсюда и `NOT NULL`;
- `target_eo`/`target_ref_text` = документ, который вносит изменение/отмену — возможно, ещё не скачан, отсюда `target_eo` нужно оставить nullable (уже так в схеме) с `target_ref_text` как текстовой заглушкой;
- `relation_type` называется **`amended_by`/`repealed_by`** (а не `amends`/`repeals`) — название явно кодирует направление «source изменён/отменён target'ом»;
- в код нужно добавить комментарий у `CREATE TABLE document_relations`, фиксирующий эту конвенцию текстом, не только в плане — иначе через полгода про неё забудут;
- **зеркальной записи при этой конвенции в принципе не возникает** — связи создаются только от лица проверяемого документа, типов `amends`/`repeals` не существует вообще. Когда позже сам изменяющий документ (`target_eo`) скачивается и проходит собственную проверку, эта проверка выдаёт его собственные правки (другие документы), а не «X изменяет Y» — записывать нечего, дедуплицировать нечего.

**Реальная проблема дедупликации — не зеркальные записи, а повторная вставка одной и той же связи при повторных проверках.** Ключ `(source_eo, relation_type, target_eo, target_ref_text)` для upsert не работает: в SQLite (и по стандарту SQL) `NULL` в `UNIQUE` не равен другому `NULL` — проверил прямым тестом, вторая строка с `target_eo = NULL` вставляется без конфликта, `upsert` её не найдёт. А когда `eoNumber` правки становится известен (после резолвинга), значение меняется с `NULL` на конкретное — тоже не совпадёт со старой строкой. `target_ref_text` тоже нестабилен как ключ: `ips.pravo.gov.ru` и `docs.cntd.ru` цитируют одну и ту же правку разным текстом.

Решение — ключ на **реквизитах правки, которые есть всегда и одинаково нормализуются в обоих источниках**: номер и дата (`onumber`/`odate` у ips, номер+дата из блока изменяющих документов у cntd).
- добавить колонки `target_number_norm` (нормализация — та же функция `normalize_number`, что уже используется в этапе 1) и `target_date`;
- уникальный ключ: `(source_eo, relation_type, target_number_norm, target_date)`;
- `target_eo` и `target_ref_text` становятся обычными дозаполняемыми полями (при повторной проверке или после резолвинга `eoNumber`), не частью ключа.
- **Остаточный, не блокирующий край**: этот ключ не различит два разных документа от разных органов с одинаковым номером и датой, оба меняющих один и тот же source — маловероятно, но теоретически возможно (та же природа коллизий, что в этапе 1). Не решается сейчас, фиксируется как известное ограничение.

**`check_id` заменяется на `last_seen_check_id`** (ссылка на последнюю проверку, в которой связь встретилась) вместо ссылки на «породившую» проверку. Если при очередной проверке связь не встретилась — её не удаляют, а помечают устаревшей (например, `stale_since`); история остаётся целиком, разбирать вручную можно в любой момент.

Отдельно (не про схему): если у правки есть `eoNumber` — стоит сразу создавать для неё запись в `documents` через обычную карточку этапа 1 (один дешёвый запрос) — тогда `target_eo` станет настоящим внешним ключом, а не текстовой заглушкой.

## Модульность: источники как заменяемые адаптеры

Закладывать источники статуса (`ips.pravo.gov.ru`, `docs.cntd.ru`, в будущем — возможно, «Гарант Коннект») за общим интерфейсом «реквизиты документа → результат проверки статуса» — чтобы при появлении доступа к платному API Гаранта его можно было подключить как ещё один адаптер без переписывания алгоритма и контракта результата.

## Политика перепроверки

Не перепроверять статус чаще, чем раз в N дней, если есть свежая строка в `document_status_checks` (N — TBD, не определено сейчас). Иначе каждое обращение к уже проверенному документу будет заново ходить по внешним сайтам без необходимости.

## Известные ограничения и открытые вопросы

- **Главный блокер** — правовой статус обращения к `docs.cntd.ru` (см. раздел выше), не решён.
- Резолвинг через `base.garant.ru` без готовой ссылки практически не работает; веб-поиск как обход даёт ~65% на маленькой выборке и требует различать `base.garant.ru` от `garant.ru/products/ipo/prime`.
- `pravo-search.minjust.ru` технически доступен (истёкший сертификат был единственной причиной прежней недоступности), но поисковый движок — легаси Java/Struts, трудозатраты на скриптование не оправданы, пока `docs.cntd.ru` (если его использование будет разрешено) даёт лучшие данные с меньшими усилиями.
- Платный официальный API «Гарант Коннект» — вариант для будущего пересмотра, закрывает резолвинг+статус+историю одним источником без каскада, но требует бюджета/доступа.
- Массовая сверка `docs.cntd.ru` vs `ips.pravo.gov.ru` сделана только на 1 документе (n=1, см. раздел выше) — не «частично» в смысле прогресса к 50–100, а фактически ещё не начата в масштабе, дающем статистическую уверенность.
- Сопоставление правки из `ips.pravo.gov.ru` с её `eoNumber` — отдельная подзадача (см. алгоритм, шаг 2), не решена автоматически.

## Порядок действий

1. Написать в АО «Кодекс» с вопросом про партнёрский доступ — закрывает блокирующий вопрос сразу для обоих этапов; заодно спросить про `/File` на `publication.pravo.gov.ru`, хотя это отдельный владелец (Минюст/ФСО, не «Кодекс») — туда отдельное обращение, если понадобится.
2. **Начинать реализацию можно уже сейчас с этапа 2a** — только `ips.pravo.gov.ru`, без блокера (там `robots.txt` не запрещает ничего). Он же сразу проверяет схему `document_status_checks`, контракт результата и конвенцию направления в `document_relations` на реальных данных.
3. Этап 2b (`docs.cntd.ru`) — после ответа от «Кодекса», после полноценной сверки на 50–100 документах (сейчас n=1), и после проверки региональных примеров сверх одного уже проверенного случая.

## Вне скоупа этапа 2

- Полнотекстовое сравнение редакций документа (что именно изменилось в тексте) — только факт изменения и его источник, не diff содержимого.
- Массовая/фоновая перепроверка статуса по всей уже скачанной базе — отдельная задача поверх этого алгоритма, если понадобится.
