# Справочник по EBPI (actual.pravo.gov.ru)

EBPI (эталонный банк правовой информации) на `actual.pravo.gov.ru` даёт
выверенный HTML-текст документа, включая таблицы с объединёнными ячейками,
независимо от того, есть ли у PDF текстовый слой. Там, где EBPI покрывает
документ, текст получается за секунды и без OCR.

Официальной документации у API нет: сведения ниже получены разбором кода сайта
(`actual.pravo.gov.ru/js/common.js`) и запросами к нему. Код клиента —
`src/npa_pipeline/ebpi.py`, конвертер в .docx — `src/npa_pipeline/ebpi_docx.py`.

## API

Базовый адрес: `http://actual.pravo.gov.ru:8000/api/ebpi/`, без авторизации.
Параметр `bpa` всегда `ebpi`.

1. `GET card/?bpa=ebpi&t={"pnum":"<eoNumber>"}` — карточка документа: `docid`,
   `docstate` («Действует без изменений» / «Действует с изменениями»),
   реквизиты. `docid: 0` с непустым `error` — документа в EBPI нет.
2. `GET redactions/?bpa=ebpi&t={"pnum":"<eoNumber>"}` — редакции документа: у
   неизменённого одна, у изменённого — по одной на каждую порцию поправок. Поля:
   `redid`, `reddate` (`YYYYMMDD`), `redinitial` (первая публикация), `actual`
   (ненадёжно, см. ниже), `redstatus`, `reddocrefid` (`docid` акта-поправки).
3. `GET redtext?bpa=ebpi&t=<redid>&ttl=0` — `{"redtext": "<html>…"}`: полный
   текст редакции. `ttl=0` — режим отображения сайта, на текст не влияет.

Карточку акта по внутреннему `docid` отдаёт тот же эндпоинт `card` с
`t={"docid":<docid>}`. Поле `docimagepath` в ней —
`http://publication.pravo.gov.ru/Document/View/<eoNumber>`, откуда берётся
`eoNumber`.

## Покрытие

Граница покрытия проходит не по уровню органа, а по виду акта:

| Вид акта | Покрыт |
|---|---|
| Федеральный закон | да |
| Указ Президента РФ | да |
| Постановление и распоряжение Правительства РФ | да |
| Акты Конституционного Суда и Верховного Суда РФ | да |
| Акты Банка России | да |
| Приказы федеральных министерств, служб, агентств | нет |
| Акты органов субъектов РФ | нет |

Таблица составлена по выборке из 23 документов и не исчерпывающая;
международные договоры как отдельный вид акта не проверялись. Для нового вида
акта покрытие стоит проверить через `fetch_card()`.

### Задержка индексации

EBPI добавляет документ не сразу после публикации на publication.pravo.gov.ru:
документ, опубликованный день-два назад, может ещё отсутствовать (наблюдалась
задержка меньше двух недель). Поэтому отрицательный результат кэшируется с
ограниченным сроком (см. «Кэш в БД»).

## Выбор редакции

`fetch_ebpi_document()` берёт действующую редакцию — с наибольшей `reddate`
среди уже вступивших в силу (`select_latest_redaction()`); редакции с датой
вступления в будущем пропускаются. Исходную публикацию возвращает
`select_initial_redaction()` (`redinitial=true`), она в основном пути не
используется.

Поле `actual` для выбора не годится: у неизменённого документа единственная
редакция бывает `actual: false`, а у изменённого `actual: true` может стоять не
там, где ожидается. `reddate` надёжна в обоих случаях.

## PDF и DOCX изменённого документа

PDF всегда остаётся исходной публикацией, а DOCX из EBPI — действующей
редакцией с поправками. Чтобы их не путать:

1. Если выбранная редакция не исходная, к имени .docx добавляется суффикс
   `(ред. от DD.MM.YYYY)`.
2. Акты-поправки (`reddocrefid` всех редакций) находятся по `docid` и
   записываются в `document_relations` (`source_eo` — акт-поправка,
   `target_eo` — изменённый документ, `relation_type='amends'`,
   `origin='ebpi'`). Акт-поправка регистрируется в `documents` минимальной
   записью по карточке EBPI, без поиска и скачивания его PDF.

Связи хранятся по каждой редакции, но в хронологию изменений не выстраиваются.

## Формат текста

`redtext` — HTML в стиле Word-экспорта (с метками `xmlns:w=…`), а не .docx.
Кнопка сайта «Сохранить в Word» заворачивает тот же HTML в
`data:application/msword,…`. Проект собирает из него настоящий .docx через
python-docx.

| Разметка | Значение |
|---|---|
| `p.T`, `p.Z` | Полужирный заголовок по центру |
| `p.C`, `p.S` | По центру |
| `p.R` | По правому краю |
| `p.I`, `p.K`, `p.H`, `p.Y` | Отступ слева (`H` — ещё и полужирный) |
| без класса, `p.P`, `p.N`, `p.J` | Обычный абзац по ширине |
| `span.W9` | Надстрочная сноска |
| `span.W4`–`W7` | Полужирный |
| `span.cmd-hide` | Перекрёстная ссылка; сохраняется только текст |
| `<td rowspan/colspan>` | Объединение ячеек |
| `<div id="topText">` | Служебная шапка просмотрщика; пропускается |

Непрямоугольное объединение ячеек не выполняется: ячейка остаётся отдельной,
текст не теряется.

## Кэш в БД

Таблица `document_ebpi` хранит по строке на `eo_number`, включая
отрицательный результат (`covered=0`): иначе каждый повторный
`fetch_document()` заново обращался бы к EBPI за приказами, которых там нет.

- Положительный результат действителен, пока сохранённый .docx есть на диске;
  если файл пропал, текст загружается заново.
- Отрицательный результат действителен `ebpi.NEGATIVE_CACHE_TTL_DAYS` (21 день)
  с запасом от наблюдавшейся задержки индексации. После этого EBPI
  запрашивается снова; если документа по-прежнему нет, срок продлевается.

## Когда EBPI документ не покрывает

`fetch_document()` пробует собрать .docx из текстового слоя PDF
(`text_layer_docx.py`), если PDF не скан. OCR нужен только настоящим сканам (см.
[`ocr-integration.md`](ocr-integration.md)).

Для НПА это почти не срабатывает: акты, которых нет в EBPI (в основном
ведомственные приказы), публикуются сканами подписанного оригинала. Для
справочников ИТС, которых в EBPI нет вовсе, это основной путь: справочники
обычно публикуются с текстовым слоем (приказы об их утверждении — сканами).

## Ограничения

- API не документировано и может измениться. Любой неожиданный ответ
  трактуется как «документа нет», отдельного сигнала «API изменилось» нет;
  резкое падение доли `covered=1` в БД — повод проверить API вручную.
- Темп запросов не калибровался: EBPI запрашивается по одному документу при
  каждом новом `fetch_document()`. Для пакетной обработки нужны паузы между
  запросами.
