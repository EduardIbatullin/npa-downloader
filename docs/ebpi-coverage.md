# Справочник по EBPI (actual.pravo.gov.ru)

Факты в этом документе получены эмпирическим тестированием (разбор минифицированного
JS сайта + прямые запросы к живому API) — официальной документации у этого API нет
вообще. Дата последней проверки указана у фактов, где это важно. На этот документ
ссылаются докстринги `ebpi.py`, `ebpi_docx.py` и `docs/ocr-integration.md`.

## Что это и зачем

EBPI («эталонный банк правовой информации») — отдельная система на
`actual.pravo.gov.ru`, не связанная напрямую с публикацией PDF на
`publication.pravo.gov.ru`. Даёт выверенный HTML-текст документа, включая таблицы
с `rowspan`/`colspan`, независимо от того, есть ли у PDF текстовый слой. Найдена
2026-10-12 — коллега обнаружил кнопку «Сохранить в Word» на странице
`http://actual.pravo.gov.ru/content/content.html#pnum=<eoNumber>` и прислал скриншот
сети браузера.

Зачем: до этого единственным способом получить текст скана без текстового слоя был
OCR (отдельный проект [npa-ocr](https://github.com/EduardIbatullin/npa-ocr)) —
часы работы, не всегда точный результат на сложных таблицах. EBPI, где покрывает,
даёт точный текст за секунды.

## API

Базовый адрес: `http://actual.pravo.gov.ru:8000/api/ebpi/` (обычный `http://`,
без авторизации). Единственное известное значение параметра `bpa` — `ebpi`.

Три эндпоинта, вызываются по порядку:

1. `GET card/?bpa=ebpi&t={"pnum":"<eoNumber>"}` → карточка документа: `docid`,
   `docstate` («Действует без изменений» / «Действует с изменениями» — это же
   закрывает часть «этапа 2», историю/статус документа), реквизиты. `docid: 0` и
   `error` непустой — документа в EBPI нет.
2. `GET redactions/?bpa=ebpi&t={"pnum":"<eoNumber>"}` → список редакций документа.
   У неизменённого документа — одна запись; у изменённого — несколько, по одной на
   каждую порцию поправок. Поля на запись: `redid`, `reddate` (`YYYYMMDD`),
   `redinitial` (true у самой первой, как опубликовано), `actual` (см.
   «Ловушка: поле `actual`» ниже), `redstatus` (человекочитаемый текст).
3. `GET redtext?bpa=ebpi&t=<redid>&ttl=0` → `{"redtext": "<html>...}"` — полный
   текст выбранной редакции, HTML в стиле Word-экспорта (см. «Формат текста» ниже).

Обнаружено разбором `actual.pravo.gov.ru/js/common.js` (функция `showDoc`, парсит
`window.location.hash` как `pnum=...`, далее `getDocCard`/`sendRequest("redtext",…)`).
`ttl=0` — режим отображения фронтенда («только действующая редакция» в терминах
сайта), на содержание текста не влияет.

Вывод: EBPI покрывает верхний ярус нормотворчества (законы, указы,
постановления/распоряжения Правительства, акты высших судов, акты Банка России).
Ведомственные приказы — любого уровня — не покрыты. Для них по-прежнему нужен OCR.
Перед использованием EBPI для нового вида акта стоит проверить `fetch_card()`, а не
полагаться на эту таблицу как на исчерпывающую классификацию.

## Выбор редакции — решение менялось

Первая версия (`select_initial_redaction`, 2026-10-12 утром) брала `redinitial=true`
— редакцию как документ был опубликован изначально. Рассуждение: для архивного
проекта текст должен совпадать с тем, что было в скачанном PDF на дату публикации.

Решение изменено в тот же день (2026-10-12 вечером) по указанию заказчика: «пока
только самый актуальный» — т.е. действующая редакция с учётом поправок, а не
исходная публикация плюс отдельно акты-поправки. `fetch_ebpi_document()` теперь
использует `select_latest_redaction()` — редакцию с максимальной `reddate`.
`select_initial_redaction()` оставлена нетронутой и протестированной на случай,
если потребуется вернуться к исходной публикации.

**Ловушка: поле `actual` не годится для выбора.** Для Постановления №190
(неизменённого) единственная редакция имеет `redinitial: true, actual: false`
(!) — сайт не считает единственную-она-же-действующую редакцию «actual» в этом
смысле поля. Для Постановления №710 (изменённого, проверено 2026-10-12) — две
редакции: `redid 473307` (`reddate: 20250901, redinitial: true, actual: false`,
исходная) и `redid 497231` (`reddate: 20260923, redinitial: false, actual: true`,
действующая). `reddate` — надёжный сигнал в обоих случаях, `actual` — нет.

## Формат текста — тот же, что «Сохранить в Word»

`redtext` — не настоящий `.docx`, а HTML с метками `xmlns:w="urn:schemas-microsoft-
com:office:word"` и т.п. (Word понимает такой HTML и открывает его как документ).
Подтверждено: кнопка «Сохранить в Word» на сайте оборачивает **тот же самый** HTML
в `data:application/msword,<urlencoded>` и даёт браузеру скачать как `.doc` — сайт
не вызывает отдельный «настоящий» docx-эндпоинт, такого эндпоинта не существует.

Разметка (калибровано по трём реальным документам — №190 без таблиц, №1430 с тремя
таблицами включая двухуровневую шапку с объединёнными ячейками, №710 изменённый):

- Классы абзацев: `p.T`/`p.Z` — жирный заголовок по центру; `p.C`/`p.S` — по
  центру; `p.R` — по правому краю; `p.I`/`p.K`/`p.H`/`p.Y` — отступ слева (`H` —
  ещё и жирным); без класса или `p.P`/`p.N`/`p.J` — обычный абзац по ширине.
- `span.W9` — надстрочная сноска; `span.W4`–`W7` — жирное начертание.
- `span.cmd-hide` с атрибутом `cmdprm="gohash=..."` — перекрёстная ссылка на другой
  пункт/документ (функция сравнения редакций на сайте); текст внутри спана виден и
  так, навигацию не сохраняем — просто текст.
- `<table>`: `rowspan`/`colspan` — обычные HTML-атрибуты, объединение ячеек через
  `cell.merge()` в python-docx (с тем же компромиссом на `InvalidSpanError`, что в
  OCR — несовпадающая геометрия объединения оставляет ячейку неслитой, текст не
  теряется).
- `<div id="topText">` в начале `<body>` — служебная шапка просмотрщика сайта
  (дублирует название документа), не часть текста акта — пропускается при
  конвертации (`ebpi_docx.py`, `convert_redtext_to_docx`).

Конвертация в `.docx` — осознанный выбор вместо повторения трюка с `.doc`: формат
получается единообразным с тем, что отдаёт OCR-пайплайн (`npa-ocr`), не зависит от
способности Word открывать HTML-под-видом-`.doc`.

## Кэш в БД

Таблица `document_ebpi` (`db.py`) — 1 строка на `eo_number`, кэширует и
**отрицательный** результат (`covered=0` — для приказов, которых большинство).
Без негативного кэша каждый повторный `fetch_document()` бил бы в сеть заново за
уже известным «не покрыт». TTL нет — запись считается верной, пока сохранённый
`.docx` физически на диске; если файл пропал, при следующем вызове перекачивается
заново (см. `service._attach_ebpi_text`). Проверено на реальной сети: первый вызов
на документе — 25,6 с (3 похода в EBPI), повторный — 0,93 с (PDF и EBPI оба из
кэша).

## Открытые вопросы

- Нет официальной документации и нет гарантий стабильности API — при изменении
  формата ответа `_request()` в `ebpi.py` трактует любой неожиданный JSON как
  «документа здесь нет» (см. `npa_pipeline.ebpi`, докстринг модуля), без явного
  сигнала «API сломался» отдельно от «документ не покрыт». Если доля `covered=True`
  в БД заметно просядет после обновления сайта — стоит проверить вручную.
- Темп запросов не калибровался на объёме (в отличие от burondt.ru, где это сделано
  намеренно) — `fetch_document()` делает EBPI-проверку на каждый **новый**
  документ, не при массовом обходе; риска повторяющейся нагрузки пока не видно, но
  если появится сценарий пакетной проверки многих документов подряд — нужно будет
  обдумать паузы между запросами.
- Таблица покрытия (14 документов) — не исчерпывающая выборка. Возможны виды актов
  вне проверенных категорий (например, акты Конституционного Суда, международные
  договоры) — поведение для них не проверено.
