# Справочник по EBPI (actual.pravo.gov.ru)

Факты в этом документе получены эмпирическим тестированием (разбор минифицированного
JS сайта + прямые запросы к живому API) — официальной документации у этого API нет
вообще. Дата последней проверки указана у фактов, где это важно. На этот документ
ссылаются докстринги `ebpi.py`, `ebpi_docx.py`, `text_layer_docx.py` и
`docs/ocr-integration.md`.

## Что это и зачем

EBPI («эталонный банк правовой информации») — отдельная система на
`actual.pravo.gov.ru`, не связанная напрямую с публикацией PDF на
`publication.pravo.gov.ru`. Даёт выверенный HTML-текст документа, включая таблицы
с `rowspan`/`colspan`, независимо от того, есть ли у PDF текстовый слой. Найдена
2026-10-12 — на странице
`http://actual.pravo.gov.ru/content/content.html#pnum=<eoNumber>` есть кнопка
«Сохранить в Word»; анализ сетевых запросов браузера при её нажатии показал
вызываемый API.

Зачем: до этого единственным способом получить текст скана без текстового слоя был
OCR (отдельный проект [npa-ocr](https://github.com/EduardIbatullin/npa-ocr)) —
часы работы, не всегда точный результат на сложных таблицах. EBPI, где покрывает,
даёт точный текст за секунды.

## API

Базовый адрес: `http://actual.pravo.gov.ru:8000/api/ebpi/` (обычный `http://`,
без авторизации). Единственное известное значение параметра `bpa` — `ebpi`.

Три эндпоинта, вызываются по порядку:

1. `GET card/?bpa=ebpi&t={"pnum":"<eoNumber>"}` → карточка документа: `docid`,
   `docstate` («Действует без изменений» / «Действует с изменениями» — это же
   закрывает часть «этапа 2», историю/статус документа), реквизиты. `docid: 0` и
   `error` непустой — документа в EBPI нет.
2. `GET redactions/?bpa=ebpi&t={"pnum":"<eoNumber>"}` → список редакций документа.
   У неизменённого документа — одна запись; у изменённого — несколько, по одной на
   каждую порцию поправок. Поля на запись: `redid`, `reddate` (`YYYYMMDD`),
   `redinitial` (true у самой первой, как опубликовано), `actual` (см.
   «Ловушка: поле `actual`» ниже), `redstatus` (человекочитаемый текст).
3. `GET redtext?bpa=ebpi&t=<redid>&ttl=0` → `{"redtext": "<html>...}"` — полный
   текст выбранной редакции, HTML в стиле Word-экспорта (см. «Формат текста» ниже).

Обнаружено разбором `actual.pravo.gov.ru/js/common.js` (функция `showDoc`, парсит
`window.location.hash` как `pnum=...`, далее `getDocCard`/`sendRequest("redtext",…)`).
`ttl=0` — режим отображения фронтенда («только действующая редакция» в терминах
сайта), на содержание текста не влияет.

## Когда EBPI не покрывает — механическое извлечение, не сразу OCR

`fetch_document()` после неудачи EBPI (`ebpi_docx_path is None`) пробует
`text_layer_docx.py` (решение 2026-10-13) — если PDF не скан (текстовый слой есть
на всех страницах), текст извлекается механически (`pypdf`), без OCR и без ИИ в
рантайме, в `Result.text_layer_docx_path`. OCR остаётся только для настоящих
сканов. Подробности алгоритма — в докстринге `text_layer_docx.py`, здесь важен
только эмпирический результат.

**На практике для НПА это почти никогда не срабатывает.** Проверено на реальной
сети на 13 приказах разных ведомств (Минприроды, ФНС, Минфин, Казначейство,
Росстат, 2026-10-13) — у всех 13 скан на 100% страниц, `text_layer_docx_path`
везде корректно остался `None`. Похоже, что граница EBPI («законы/постановления/
указы — да, приказы — нет») практически совпадает с границей «есть исходный
электронный документ — да, только скан подписанного оригинала — нет»: то, что
EBPI не покрывает, в основном и есть то, что всегда сканируют. Так что для НПА
этот механизм — корректный защитный код на случай исключения (или будущего вида
акта), а не реально работающий основной путь.

**Для ИТС/НДТ (burondt.ru) — наоборот, основной путь.** У ИТС нет `eoNumber`,
EBPI к ним структурно неприменим, но справочники (не путать с приказами об
утверждении — они почти всегда сканы) обычно не сканы: проверено на ИТС 28-2021
(180 страниц, 2026-10-13) — `has_full_text_layer() -> True`, извлечение дало
8386 абзацев настоящего читаемого текста. Подключено к `fetch_its()`/
`fetch_its_by_url_id()` (`its_download.py`) — `ItsFileResult.text_layer_docx_path`.

**Задержка индексации у самых свежих документов.** Распоряжение №2874-р от
10.10.2026 (опубликовано 12.10.2026, проверено в тот же день) `fetch_card()` не
нашёл — `docid: 0`. Тот же вид акта двухнедельной давности (4 распоряжения от
26.09.2026) найден без исключений. Значит EBPI индексирует документ не мгновенно
после публикации на publication.pravo.gov.ru — у совсем свежих (день-два) документов
`fetch_card() -> None` может означать «пока не попал в EBPI», а не «этот вид акта не
покрывается». Конкретный лаг не измерен (знаем только «больше 0, меньше 2 недель»).
Последствие для `fetch_document()`: если документ скачивается в день публикации,
`ebpi_docx_path` может остаться `None` даже для покрытого вида акта — повторный
вызов позже может дать другой результат (кэш в БД это допускает: `document_ebpi`
переоценивается, если файла нет на диске, но текущая реализация не переобращается
в сеть просто по истечении времени для уже закэшированного отрицательного
результата — см. открытый вопрос ниже).

## Выбор редакции — решение менялось

Первая версия (`select_initial_redaction`, 2026-10-12 утром) брала `redinitial=true`
— редакцию как документ был опубликован изначально. Рассуждение: для архивного
проекта текст должен совпадать с тем, что было в скачанном PDF на дату публикации.

Решение изменено в тот же день (2026-10-12 вечером): нужна только действующая
редакция с учётом поправок, а не исходная публикация плюс отдельно акты-поправки.
`fetch_ebpi_document()` теперь
использует `select_latest_redaction()` — редакцию с максимальной `reddate`.
`select_initial_redaction()` оставлена нетронутой и протестированной на случай,
если потребуется вернуться к исходной публикации.

**Ловушка: поле `actual` не годится для выбора.** Для Постановления №190
(неизменённого) единственная редакция имеет `redinitial: true, actual: false`
(!) — сайт не считает единственную-она-же-действующую редакцию «actual» в этом
смысле поля. Для Постановления №710 (изменённого, проверено 2026-10-12) — две
редакции: `redid 473307` (`reddate: 20250901, redinitial: true, actual: false`,
исходная) и `redid 497231` (`reddate: 20260923, redinitial: false, actual: true`,
действующая). `reddate` — надёжный сигнал в обоих случаях, `actual` — нет.

## PDF (исходный) и DOCX (действующая редакция) — не одно и то же

Следствие решения выше: PDF всегда остаётся исходной публикацией (так и должно
быть — это архив), а DOCX из EBPI для изменённого документа содержит текст с
поправками. Одинаковые имена файлов вводили бы в заблуждение — выглядело бы как
«тот же документ в двух форматах», хотя это два разных по содержанию текста.
Решение (2026-10-12):

1. **Имя файла помечается, если показана не исходная редакция.** Если
   `EbpiDocument.is_initial is False`, `service._attach_ebpi_text` добавляет в имя
   `.docx` суффикс `(ред. от DD.MM.YYYY)` (дата — `EbpiDocument.red_date`,
   `ebpi.format_red_date`). Для неизменённых документов (большинство) суффикса нет
   — PDF и DOCX и так совпадают по содержанию.
2. **Акт-поправка резолвится и записывается в БД**, а не теряется молча. У
   изменённой редакции `reddocrefid` (ненулевой) — это `docid` самого акта-поправки
   внутри EBPI. Отдельного эндпоинта «дай мне eoNumber по docid» нет, но
   `card/?bpa=ebpi&t={"docid":<reddocrefid>}` (тот же эндпоинт card, другая форма
   параметра `t`) работает и отдаёт карточку акта-поправки — включая
   `docimagepath` вида `http://publication.pravo.gov.ru/Document/View/<eoNumber>`,
   откуда вытаскивается `eoNumber`. Проверено на Постановлении №710: `reddocrefid
   333140` → карточка «Постановление Правительства Российской Федерации от
   23.09.2026 № 1221 "О внесении изменения в постановление ... № 710"»,
   `eoNumber 0001202609230028`. Третий `.docx` (исходная редакция EBPI) при этом
   сознательно не скачивается — это было бы дублированием уже скачанного PDF в
   другом формате, не несёт новой информации (решение того же обсуждения).

Реализация — `ebpi.resolve_amending_acts()` (по всем редакциям с ненулевым
`reddocrefid`, с дедупликацией по `docid`) и `DocumentStore.record_relation()` —
пишет в ранее не используемую таблицу `document_relations` (`source_eo` = акт-
поправка, `target_eo` = изменённый документ, `relation_type='amends'`,
`origin='ebpi'`). Сам акт-поправка регистрируется в `documents` минимальной
записью (`upsert_from_doc_item` на данных из карточки EBPI — `adoptions[0]`,
`docname`, `docpassing`), не через полный поиск на publication.pravo.gov.ru:
`document_relations` требует оба `eo_number` внешним ключом (FK), а отдельно
искать и скачивать PDF акта-поправки не входит в эту задачу.

Резолвится только акт, который ввёл **выбранную** (последнюю) редакцию — если у
документа несколько раундов поправок, в БД попадёт связь на каждый раунд
(`resolve_amending_acts` проходит по всем редакциям, не только по последней), но
полная цепочка «что когда поменяло» по-прежнему не выстраивается в хронологию —
это сырые связи, не версионная история.

## Формат текста — тот же, что «Сохранить в Word»

`redtext` — не настоящий `.docx`, а HTML с метками `xmlns:w="urn:schemas-microsoft-
com:office:word"` и т.п. (Word понимает такой HTML и открывает его как документ).
Подтверждено: кнопка «Сохранить в Word» на сайте оборачивает **тот же самый** HTML
в `data:application/msword,<urlencoded>` и даёт браузеру скачать как `.doc` — сайт
не вызывает отдельный «настоящий» docx-эндпоинт, такого эндпоинта не существует.

Разметка (калибровано по трём реальным документам — №190 без таблиц, №1430 с тремя
таблицами включая двухуровневую шапку с объединёнными ячейками, №710 изменённый):

- Классы абзацев: `p.T`/`p.Z` — жирный заголовок по центру; `p.C`/`p.S` — по
  центру; `p.R` — по правому краю; `p.I`/`p.K`/`p.H`/`p.Y` — отступ слева (`H` —
  ещё и жирным); без класса или `p.P`/`p.N`/`p.J` — обычный абзац по ширине.
- `span.W9` — надстрочная сноска; `span.W4`–`W7` — жирное начертание.
- `span.cmd-hide` с атрибутом `cmdprm="gohash=..."` — перекрёстная ссылка на другой
  пункт/документ (функция сравнения редакций на сайте); текст внутри спана виден и
  так, навигацию не сохраняем — просто текст.
- `<table>`: `rowspan`/`colspan` — обычные HTML-атрибуты, объединение ячеек через
  `cell.merge()` в python-docx (с тем же компромиссом на `InvalidSpanError`, что в
  OCR — несовпадающая геометрия объединения оставляет ячейку неслитой, текст не
  теряется).
- `<div id="topText">` в начале `<body>` — служебная шапка просмотрщика сайта
  (дублирует название документа), не часть текста акта — пропускается при
  конвертации (`ebpi_docx.py`, `convert_redtext_to_docx`).

Конвертация в `.docx` — осознанный выбор вместо повторения трюка с `.doc`: формат
получается единообразным с тем, что отдаёт OCR-пайплайн (`npa-ocr`), не зависит от
способности Word открывать HTML-под-видом-`.doc`.

## Кэш в БД

Таблица `document_ebpi` (`db.py`) — 1 строка на `eo_number`, кэширует и
**отрицательный** результат (`covered=0` — для приказов, которых большинство).
Без негативного кэша каждый повторный `fetch_document()` бил бы в сеть заново за
уже известным «не покрыт». Положительный результат (`covered=1`) считается верным,
пока сохранённый `.docx` физически на диске; если файл пропал, при следующем
вызове перекачивается заново (см. `service._attach_ebpi_text`). Проверено на
реальной сети: первый вызов на документе — 25,6 с (3 похода в EBPI), повторный —
0,93 с (PDF и EBPI оба из кэша).

**У отрицательного результата TTL — `ebpi.NEGATIVE_CACHE_TTL_DAYS = 21`** (решение
2026-10-13, в ответ на находку «Задержка индексации» выше). Если `covered=0` и
`checked_at` старше 21 дня, `_attach_ebpi_text` пробует сеть ещё раз, а не доверяет
старой записи навсегда — иначе документ, скачанный в день публикации, мог бы
остаться помеченным «не покрыт» даже после того, как EBPI его проиндексирует. Окно
калибровано с запасом от единственного наблюдённого случая лага (меньше 2 недель);
если документ так и не найдётся после истечения TTL, `checked_at` обновляется и
окно просто продлевается — приказы (большинство документов, никогда не появляющиеся
в EBPI) платят повторным запросом раз в 21 день, не на каждый `fetch_document()`.

## Открытые вопросы

- Нет официальной документации и нет гарантий стабильности API — при изменении
  формата ответа `_request()` в `ebpi.py` трактует любой неожиданный JSON как
  «документа здесь нет» (см. `npa_pipeline.ebpi`, докстринг модуля), без явного
  сигнала «API сломался» отдельно от «документ не покрыт». Если доля `covered=True`
  в БД заметно просядет после обновления сайта — стоит проверить вручную.
- Темп запросов не калибровался на объёме (в отличие от burondt.ru, где это сделано
  намеренно) — `fetch_document()` делает EBPI-проверку на каждый **новый**
  документ, не при массовом обходе; риска повторяющейся нагрузки пока не видно, но
  если появится сценарий пакетной проверки многих документов подряд — нужно будет
  обдумать паузы между запросами.
- Таблица покрытия (23 документа) — всё ещё не исчерпывающая выборка. Акты
  Конституционного Суда, Указы Президента и Распоряжения Правительства проверены
  и добавлены 2026-10-13; международные договоры как отдельный вид акта
  (документ-соглашение, а не федеральный закон о его ратификации) — ещё не
  проверены.
- ~~Негативный кэш не протухает по времени~~ — исправлено 2026-10-13, TTL
  `ebpi.NEGATIVE_CACHE_TTL_DAYS = 21` (см. «Кэш в БД» выше). Окно калибровано с
  запасом от единственного наблюдённого случая лага — если на практике найдётся
  документ с более длинным лагом индексации, окно нужно будет пересмотреть.
