# Справочник по API publication.pravo.gov.ru

Сведения получены запросами к API: официальная документация в ряде мест описывает параметры, которые не работают. Клиент — `src/npa_pipeline/api.py`, алгоритм поиска — [`search-algorithm.md`](search-algorithm.md).

Базовый адрес: `http://publication.pravo.gov.ru` (именно `http://`, не `https://` — при работе из некоторых окружений `https` зависает на уровне TCP-соединения; сам сервер по HTTPS может работать нормально, это ограничение конкретных клиентских окружений, не сервера).

Эндпоинты: `/api/Documents` (поиск/список), `/api/Document?eoNumber=X` (карточка документа, включает полный список органов-подписантов), `/api/SignatoryAuthorities`, `/api/DocumentTypes`, `/api/Categories`, `/api/PublicBlocks` (справочники), `/file/pdf?eoNumber=X` (скачивание PDF — не описан в официальной документации, найден эмпирически, работает).

## Параметры `/api/Documents`, которые фильтруют на сервере

- `SignatoryAuthorityId` — фильтрует корректно. Для совместных документов (несколько подписавших органов) совпадает по **любому** из органов в списке подписантов, не только по основному (`isMain: true`).
- `Number` + `NumberSearchType` (`0`=точное совпадение, `1`=начинается с, `2`=заканчивается на, `3`=содержит) — все четыре режима работают.
- `EoNumber` — работает и на списочном эндпоинте, не только в карточке документа.
- `JdRegNumber` — номер регистрации в Минюсте, точное совпадение, работает.
- `PageSize` — работает, но принимает только значения 10/30/100/200.
- `Index` — номер страницы с 1 (`currentPage`/`pagesTotalCount` корректны, страницы не пересекаются).

## Параметры, которые сервер игнорирует (хотя они есть в документации)

- `DocumentDateFrom`/`DocumentDateTo`, `PublishDateFrom`/`PublishDateTo`, `JdRegDateFrom`/`JdRegDateTo`, `PeriodType`+`Date` — все варианты фильтрации по датам не работают, нужна клиентская фильтрация.
- `ComplexName` — не работает как текстовый поиск (документ описывает его как поиск по составному названию, включающему орган; на практике запрос с точным номером + `ComplexName` с посторонним текстом даёт тот же результат, что и без `ComplexName`).
- `DocumentTypeId` — не фильтрует: правильный и заведомо неправильный GUID типа дают одинаковое число результатов. Тип проверяется на клиенте по полю `documentTypeId`.
- `SortDestination` — не влияет на порядок результатов.

## Формат номера документа (`Number`)

- Сервер сравнивает **точную строку**, без числовой нормализации: `"0402"` и `" 402"` НЕ совпадают с реальным номером `"402"` (0 результатов в обоих случаях).
- Регистр букв в номере (например, суффикс `ФЗ`/`фз`) **не влияет** на совпадение — сравнение регистронезависимое.
- Тип тире/дефиса **влияет**: типографское тире `–` (U+2013) вместо обычного ASCII-дефиса `-` в запросе даёт 0 результатов там, где документ реально существует с ASCII-дефисом.
- В выборке из 2087 номеров (Президент РФ, Минприроды) нетипичных тире в данных сервера нет: проблема почти всегда в запросе. Выборка не исчерпывающая, поэтому на клиенте нормализуются обе стороны сравнения.

## Поиск по номеру без указания органа

`GET /api/Documents?Number=X&NumberSearchType=0` без `SignatoryAuthorityId` ищет по документам всех органов. Объём ответа приемлем даже для самых частых номеров: `Number=402` — 672 результата (4 страницы по 200), `Number=1` — 3430 (18 страниц). Это дешевле, чем запрос по каждому органу-кандидату.

## Совпадения номеров

- Орган может повторно использовать номер в разные годы: у приказов Минприроды России № 402 есть документ от 19.07.2016 (`eoNumber = 0001201609130025`) и от 20.07.2026 (`eoNumber = 0001202609240005`).
- Номера федеральных законов (`NNN-ФЗ`) повторяются **каждый год**: запрос «Президент РФ + номер `310-ФЗ`» возвращает по документу на каждый год с 2017 по 2026 (`eoNumber`: `0001201710300036` (2017), `0001201808030096` (2018), `0001201908020082` (2019), `0001202010010005` (2020), `0001202107020029` (2021), `0001202207140081` (2022), `0001202307100038` (2023), `0001202408080120` (2024), `0001202507310060` (2025), `0001202608040033` (2026)).
- Поэтому отбор по точной дате подписания на клиенте обязателен практически для любого поиска по органу и номеру.

## Совместные (многосторонней подписи) документы

Документ с несколькими подписавшими органами находится через `SignatoryAuthorityId` **любого** из них с одинаковым `eoNumber` (например, совместный приказ Минприроды России и Роснедра № 247/04, `eoNumber = 0001202306010022`). Если поиск ведётся сразу по нескольким кандидатам-органам, такой документ будет найден несколько раз (по разу на каждого подписанта из списка кандидатов) — требуется дедупликация результатов по `eoNumber` перед тем, как считать результат неоднозначным.

### Подписанты в списке и в карточке

- Элемент ответа `/api/Documents` содержит только **основной** `signatoryAuthorityId` (GUID органа с `isMain: true`). Полного массива подписантов в списке **нет**.
- Карточка `/api/Document?eoNumber=X` содержит массив `signatoryAuthorities` (`id`, `name`, `isMain`, `weight`) — полный список соподписантов.

Следствие для клиентской фильтрации: если поиск шёл **без** `SignatoryAuthorityId`, а кандидат-GUID — не основной подписант, нельзя сужать только по `signatoryAuthorityId` из списка — совместный документ отфильтруется ошибочно. После фильтрации по дате (обычно остаётся 0–несколько записей) нужно догрузить карточку и сверять кандидатов с полным `signatoryAuthorities`. Если поиск шёл **с** `SignatoryAuthorityId` одного кандидата — сервер уже отфильтровал корректно, повторное сужение по полю списка не нужно (и вредно: в списке всё равно основной GUID).

## Справочник органов

- `GET /api/SignatoryAuthorities` **без параметров** возвращает полный список (~3986 записей) с полями `id`, `name`, `weight`. Этого достаточно для построения локального кэша резолвинга.
- `GET /api/PublicBlocks` возвращает дерево блоков; вложенные `categories` часто пусты, `GET /api/Categories` на практике отвечает 400 — обход PublicBlocks → Categories → SignatoryAuthorities для полного списка органов не обязателен.

## Первичный ключ документа — `eoNumber`

Каждый элемент ответа `/api/Documents` содержит поле `eoNumber` (например, `0001202609240005` = `0001` + дата публикации `20260924` + порядковый номер за день `0005`). Это внутренний идентификатор системы публикации, присваиваемый в момент размещения документа на портале, а не самим органом-издателем — дата в `eoNumber` это дата **публикации**, а не дата подписания документа (`documentDate`), они могут различаться. `eoNumber` невозможно вычислить заранее по реквизитам документа (орган, номер, дата подписания) — обратного поиска по этим данным в API нет; он становится известен либо как результат обычного поиска (уже есть в каждом найденном элементе), либо из внешней ссылки вида `http://publication.pravo.gov.ru/document/{eoNumber}`. Если `eoNumber` уже известен — это самый быстрый и однозначный способ получить документ: `/api/Document?eoNumber=X` (карточка) или `/file/pdf?eoNumber=X` (сам файл).

## Граница охвата по времени

Самые старые документы в системе подписаны 07–08.11.2011 и опубликованы 10.11.2011 — это дата запуска портала. Документы, подписанные раньше этой границы, в системе отсутствуют в принципе — нужен другой источник. Важно: граница определяется датой **публикации** на портале, а не датой подписания документа — документ, подписанный до 08.11.2011, но опубликованный позже этой даты (например, с задержкой), в системе может быть. Поэтому нельзя заранее (до попытки поиска) отсекать запрос по дате подписания — сначала всегда нужно выполнить поиск, и только при отсутствии результата и дате подписания раньше границы возвращать явный статус «вне охвата системы», а не путать его с «документ не найден».

Отдельное от системной границы явление: у конкретного органа самая ранняя запись в системе может быть значительно позже 2011 года (например, у Минприроды России самая старая запись в выборке — начало 2015 года) — это не сигнал о другой системной границе, а особенность того, когда конкретный орган начал публиковаться под своим нынешним идентификатором (переименование, реорганизация и т.п.).

## Прочие технические ограничения

- Формат документа на сервере — всегда PDF, других форматов (DOCX/RTF) нет.
- Крупные PDF (30+ МБ) могут обрезаться при коротком таймауте скачивания — нужен таймаут 120–180 секунд и проверка целостности после скачивания.
- При частых запросах без пауз бывают обрывы соединения (около 10 % из 30 запросов подряд); HTTP-клиент повторяет запросы с нарастающей паузой.
- `documentDate`/`publishDateShort` — время всегда `T00:00:00`, сдвигов часового пояса нет (выборка из 400 документов).
